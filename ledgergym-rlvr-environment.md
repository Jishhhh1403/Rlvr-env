# LedgerGym
### An RLVR Training Environment for Verifiable Financial Reasoning

**Version:** 0.1 (Draft) | **Date:** 2026-10-14 | **Status:** Concept / project planning

---

## 1. Summary

**LedgerGym** is a procedurally generated reinforcement learning environment in which a small language model solves bank-style financial tasks, and a deterministic Python verifier scores every answer. It uses **RLVR (Reinforcement Learning with Verifiable Rewards)**: rewards come from code that can prove an answer right or wrong, with no human labels and no learned reward model.

Finance is a strong fit for RLVR because most quantitative questions (loan math, reconciliation, trend rules) have a provably correct answer. Because tasks are generated by code, the generator already knows the ground truth, which means:

- Verification is simple and exact
- Training data is effectively unlimited
- Difficulty can be controlled precisely

**Goals**
1. Build a reusable Gym-style environment with multiple financial task families
2. Train a small LLM with GRPO and show measurable improvement over baseline
3. Demonstrate research-quality practices: curriculum learning, shaped rewards, reward-hacking analysis, ablations

**Non-goals**
- Not a production financial advisory system
- Not trained or evaluated on real customer data (all data is synthetic)

---

## 2. Background: Why RLVR

| Approach | Reward source | Limitation |
|---|---|---|
| RLHF | Learned reward model from human preferences | Costly labels; reward model can be exploited |
| RLAIF | Another LLM as judge | Judge bias and noise |
| **RLVR** | **Programmatic verifier** | Only works where answers are checkable |

RLVR gives a clean, hard-to-argue-with signal. The main engineering risk shifts from "noisy reward" to **"reward hacking"**: the model finding ways to score well without actually solving the task. Managing that risk is a central part of this project.

## 3. Task Families

Start with three families. Each defines a **generator** (creates the problem and its hidden truth) and a **verifier** (scores the response).

### 3.1 Loan Math
Compute exact quantities from loan terms.

| Variant | Example question | Verification |
|---|---|---|
| EMI calculation | "Principal 5,00,000, 9.5% annual rate, 36 months. What is the EMI?" | Closed-form formula, tolerance of 1 currency unit |
| Remaining principal | "After 14 payments, what is the outstanding principal?" | Amortization schedule |
| Prepayment impact | "A one-time prepayment of 50,000 after month 12. New tenure / total interest?" | Re-run amortization |
| Rate comparison | "Which of these two offers has lower total cost?" | Compute both, compare |

**Difficulty knobs:** number of loans, prepayments, rate changes (floating), fees, rounding conventions.

### 3.2 Statement Reconciliation
Given a transaction list, find the discrepancy.

| Variant | Example question |
|---|---|
| Duplicate charge | "Identify the duplicated transaction ID." |
| Missing deposit | "The closing balance is off by X. Which expected credit is missing?" |
| Balance mismatch | "At which transaction does the running balance first diverge from the bank's stated balance?" |

**Difficulty knobs:** transaction count, distractor fields, near-duplicate decoys (same amount, different merchant/date), mixed currency and date formats, noisy merchant names.

### 3.3 Trend Questions
Given 6 months of transactions, answer a financial-health question using a **defined rule**.

Example: *"Is the customer's liquidity improving, stable, or deteriorating?"*

The verifier applies the exact rule (e.g. slope of balance-buffer-days over 90 days against thresholds). This is the same logic as in a separate Financial State Engine project, so the two projects reinforce each other and make a coherent story for a bank audience.

**Difficulty knobs:** series length, noise level, seasonality, one-off shocks (bonus, large purchase) that should not flip the label.

## 4. Architecture

```
Task generator (seeded, difficulty-parameterized)
            |
            v
   Prompt + hidden ground truth
            |
            v
 Policy model (small LLM)  --->  response
            |
            v
 Parser (strict output format, <answer>...</answer>)
            |
            v
 Verifier (deterministic Python)  --->  reward + diagnostics
            |
            v
 GRPO trainer updates policy
            ^
            |
 Curriculum controller (adjusts difficulty from rolling pass rate)
```

### 4.1 Gym-style interface

```python
class LedgerEnv:
    def reset(self, seed: int, family: str, difficulty: int) -> Task: ...
    def step(self, response: str) -> StepResult: ...   # reward, info, done

class Task(BaseModel):
    prompt: str
    family: str
    difficulty: int
    seed: int
    # ground truth is held inside the env, never exposed to the policy

class StepResult(BaseModel):
    reward: float
    components: dict[str, float]   # per-component breakdown
    info: dict                     # parse errors, diagnostics
    done: bool = True
```

Design principles:
- **Deterministic by seed:** any task and score can be reproduced exactly
- **Ground truth never in the prompt or in any logged field the policy can see**
- **Per-component reward breakdown** logged for every sample, which is essential for debugging

### 4.2 Output format
The policy must respond with reasoning, then a final answer in a strict schema:

```
<reasoning> ...free text... </reasoning>
<answer> {"emi": 16012.45} </answer>
```

Parsing is strict: malformed output scores zero on correctness. Answers use JSON so numeric and categorical results parse unambiguously.

## 5. Reward Design

### 5.1 Baseline reward

| Component | Weight | Check |
|---|---|---|
| Final answer correct | 0.80 | Numeric within tolerance, or exact label/ID match |
| Valid output format | 0.10 | Schema and tag validation |
| Intermediate fields correct | 0.10 | e.g. correct month identified, correct sub-quantity |
| Length penalty | up to -0.10 | Applied to empty or overlong output |

**Rule:** correctness must dominate, so format and intermediate credit alone can never beat a correct answer, and cannot be farmed.

### 5.2 Reward variants to ablate
1. **Binary:** 1 if correct, else 0
2. **Shaped:** the table above
3. **Shaped + tolerance gradient:** partial credit decaying with relative error on numeric answers

### 5.3 Reward-hacking defenses (built in from day one)
| Potential hack | Defense |
|---|---|
| Guessing a plausible number without work | Hold-out and randomized parameters make guessing near-impossible; track pass rate vs. reasoning length |
| Format farming | Cap format weight; zero out correctness on malformed answers |
| Emitting multiple answers to cover options | Accept only one `<answer>` block; penalize extras |
| Degenerate answers that match a common label | Balanced label distribution in the generator; monitor label entropy of outputs |
| Exploiting verifier tolerance | Tolerance tuned per task; tested with adversarial near-miss answers |
| Prompt leakage of truth | Automated test that ground truth strings never appear in prompts |

## 6. Curriculum Learning

Each task family exposes an integer **difficulty level** (e.g. 1-10) controlling the generator knobs.

**Controller logic (simple version)**
- Track rolling pass rate over the last N episodes per family
- If pass rate > 70%: increase difficulty
- If pass rate < 30%: decrease difficulty
- Otherwise: hold
- Always mix in a small share (about 10-20%) of easier tasks to prevent forgetting

**Ablation:** fixed-difficulty vs. curriculum training, compared on the same held-out evaluation set.

## 7. Optional Extensions (Innovation Layer)

These are what make the project distinctive beyond "GSM8K plus GRPO."

### 7.1 Tool use
Give the model a calculator and/or a sandboxed pandas tool. Reward correct tool-assisted answers. Research question: *does RL teach the model when to use a tool rather than compute mentally?*

### 7.2 Self-adversarial generator
A second process searches generator parameters to find tasks the current policy fails, and feeds them back into training. The environment hardens as the policy improves.

### 7.3 Cross-family transfer
Train on loan math only; evaluate zero-shot on reconciliation and trend tasks. Does verifiable numeric reasoning transfer?

### 7.4 Process-level verification
For loan math, verify intermediate steps (e.g. monthly rate, number of periods) from the reasoning text where parseable, and report how often a correct final answer comes from correct reasoning.

## 8. Evaluation Plan

### 8.1 Held-out sets
- **Frozen evaluation seeds** never used in training, generated per family and per difficulty level
- Separate **out-of-distribution set** (unseen formats, larger sizes) to test generalization

### 8.2 Metrics

| Metric | Purpose |
|---|---|
| Pass rate per family and difficulty | Core capability |
| Mean reward (and per-component) | Training signal health |
| Format-validity rate | Detect format collapse |
| Output length distribution | Detect verbosity or hack drift |
| Pass@k (k = 1, 4, 8) | Sampling robustness |
| Tool-call rate and accuracy (if enabled) | Tool-use learning |
| Label entropy of outputs (trend task) | Detect degenerate answers |

### 8.3 Required comparisons
1. Untrained baseline vs. trained policy
2. Binary vs. shaped reward
3. Fixed difficulty vs. curriculum
4. In-distribution vs. out-of-distribution
5. (Optional) Frontier-model reference score on the same eval set for context

## 13. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Verifier bugs silently reward wrong answers | Property-based tests; cross-check against independent implementations (e.g. a financial library) |
| Reward hacking | Built-in defenses (Section 5.3); inspect samples manually every run |
| Small models can't learn the task (all-zero rewards) | Start at low difficulty so there is a nonzero baseline pass rate; GRPO needs reward variance within groups |
| Training instability or collapse | Conservative learning rate, KL penalty, frequent eval checkpoints |
| Overfitting to the generator's templates | Prompt paraphrase variety; out-of-distribution eval set |
| Compute limits | Small models, LoRA, short sequences; scale difficulty rather than model size |
| Results not reproducible | Seeded generators, pinned dependencies, logged configs |

## Appendix A: Loan Math Generator and Verifier (sketch)

```python
import random
from pydantic import BaseModel

def emi(principal: float, annual_rate: float, months: int) -> float:
    r = annual_rate / 12 / 100
    return principal * r * (1 + r) ** months / ((1 + r) ** months - 1)

class LoanTask(BaseModel):
    prompt: str
    truth: float  # held privately by the env

def generate(seed: int, difficulty: int) -> LoanTask:
    rng = random.Random(seed)
    principal = rng.randrange(100_000, 2_000_000, 5_000)
    rate = round(rng.uniform(7.0, 16.0), 2)
    months = rng.choice([12, 24, 36, 48, 60, 84])
    truth = round(emi(principal, rate, months), 2)
    prompt = (
        f"A loan of {principal:,} at {rate}% annual interest is repaid in "
        f"{months} equal monthly instalments. Compute the EMI. "
        'Respond with <answer>{"emi": <number>}</answer>.'
    )
    return LoanTask(prompt=prompt, truth=truth)

def verify(response: str, truth: float, tol: float = 1.0) -> dict:
    import json, re
    m = re.findall(r"<answer>(.*?)</answer>", response, re.S)
    if len(m) != 1:
        return {"format": 0.0, "correct": 0.0}
    try:
        val = float(json.loads(m[0])["emi"])
    except Exception:
        return {"format": 0.0, "correct": 0.0}
    return {"format": 1.0, "correct": 1.0 if abs(val - truth) <= tol else 0.0}

def reward(parts: dict) -> float:
    return 0.8 * parts["correct"] + 0.1 * parts["format"]
```

## Appendix B: Glossary

- **RLVR:** reinforcement learning where rewards come from programmatic verification of outputs.
- **GRPO:** Group Relative Policy Optimization; samples a group of responses per prompt and uses relative rewards within the group, with no separate value model.
- **Reward hacking:** achieving high reward without achieving the intended behavior.
- **Curriculum learning:** progressively increasing task difficulty as the policy improves.
- **Pass@k:** probability that at least one of k sampled responses is correct.
- **Verifier:** deterministic code that checks whether a response is correct.
