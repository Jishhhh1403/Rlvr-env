# LedgerGym

### An RLVR Training Environment for Verifiable Financial Reasoning

**LedgerGym** is a procedurally generated reinforcement learning environment in which a
small language model solves bank-style financial tasks and a deterministic Python
verifier scores every answer. It uses **RLVR (Reinforcement Learning with Verifiable
Rewards)**: rewards come from code that can prove an answer right or wrong, with no human
labels and no learned reward model.

> *A synthetic, fully verifiable training ground for financial reasoning: every reward is
> provable, every task is reproducible.*

---

## Why RLVR for finance

Most quantitative finance questions (loan math, reconciliation, trend rules) have a
provably correct answer. Because tasks are generated by code, the generator already knows
the ground truth, so verification is exact, training data is effectively unlimited, and
difficulty is controllable.

| Approach | Reward source | Limitation |
|---|---|---|
| RLHF | Learned reward model from human preferences | Costly labels; reward model can be exploited |
| RLAIF | Another LLM as judge | Judge bias and noise |
| **RLVR** | **Programmatic verifier** | Only works where answers are checkable |

The main engineering risk shifts from noisy reward to **reward hacking**. Feasible
robustness is built in from day one (see [docs/reward_hacking_log.md](docs/reward_hacking_log.md)).

---

## Task families

| Family | Variants | Verification |
|---|---|---|
| **Loan Math** | EMI, remaining principal, prepayment impact, offer comparison | Closed-form loan math, cross-checked against an independent month-by-month amortization |
| **Reconciliation** | duplicate charge, missing deposit, running-balance mismatch | Exact ID / sub-quantity matching |
| **Trend** | liquidity label (improving / stable / deteriorating) | Published balance-buffer-days slope rule |

Each family exposes an integer **difficulty level 1-10** that controls generator knobs
(sizes, noise, fees, decoys, shocks).

## Quickstart

```python
import json
from ledgergym import LedgerEnv

env = LedgerEnv()                                  # loads configs/default.yaml
task = env.reset(seed=42, family="loan_math", difficulty=3)
print(task.prompt)

response = '<reasoning>...</reasoning><answer>{"emi": 16012.45}</answer>'
result = env.step(response)

print(result.reward, result.components)            # scalar reward + per-component breakdown
print(result.info["passed"], result.info["verify"])  # pass flag + full diagnostics
```

Notes:

- Deterministic by seed: any task and score can be replayed exactly.
- Ground truth never appears in the prompt and is never logged where the policy can see it.
- `env.step` returns `done=True`; this is a single-turn environment.

## Reward design

| Component | Weight | Check |
|---|---|---|
| Final answer correct | 0.80 | Numeric within tolerance, or exact label/ID match |
| Valid output format | 0.10 | Exactly one `<answer>` block, JSON object, scalar values |
| Intermediate fields correct | 0.10 | Sub-quantities (EMI, monthly rate, buffer days, ...) |
| Length penalty | up to -0.10 | Applied to empty or overlong output |

Three reward modes are available for ablation: `binary`, `shaped` (default), and
`gradient` (partial credit decaying with relative error on the primary numeric field).
Correctness dominates: format + intermediate credit alone can never beat a correct answer,
and malformed output zeroes correctness so format cannot be farmed.

## Curriculum

`CurriculumController` raises or lowers the difficulty per family from a rolling pass rate
(> 70% up, < 30% down, otherwise hold) and mixes in ~15% easier episodes to prevent
forgetting. Fixed-difficulty versus curriculum training is a required ablation.

## Evaluation

```bash
# Freeze held-out seeds (one file per family/difficulty split)
python -m ledgergym.eval.make_frozen_seeds

# Evaluate a policy over the frozen seeds
python -m ledgergym.eval.run_eval --policy random
python -m ledgergym.eval.run_eval --policy model --model-name Qwen/Qwen2.5-0.5B-Instruct --k 4
```

Reported metrics: pass rate per family and difficulty, mean reward and per-component
means, format-validity rate, output-length distribution, pass@k, and label entropy.
An out-of-distribution split (unseen formats, larger sizes) is generated separately.

### Baseline snapshot (sanity bounds, not a trained model)

Measured on the frozen held-out set (150 in-distribution + 24 out-of-distribution
episodes) with the shipped runner:

| Policy | pass@1 | pass@4 | mean reward | format validity |
|---|---|---|---|---|
| Oracle (uses ground truth) | 1.000 | 1.000 | 1.000 | 1.000 |
| Random (valid format, random values) | 0.000 | 0.000 | 0.100 | 1.000 |

The oracle proves the verifiers accept every ground-truth answer on both splits; the
random policy's 0.10 shows the format credit alone (and is a live example of the
format-farming signal that `hack_monitor` tracks). Replace these rows with
untrained-vs-trained results once GRPO runs are available.

## Training (GRPO)

```bash
pip install -e ".[train]"
python -m ledgergym.train.grpo_train --config ledgergym/train/configs/grpo_shaped.yaml
```

The reward function inside `grpo_train.py` wraps `LedgerEnv`: prompts are generated from
seeds, so the trainer regenerates ground truth instead of ever storing it in the dataset.

(near-miss answers), malformed-output handling, and an automated check that ground truth
never leaks into prompts.
